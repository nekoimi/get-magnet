# 采集平台 v2.0 优化方案

## 1. 文档目的

本文档定义 get-magnet v2.0 的整体改造方向、核心边界、数据库模型和迁移策略。

v2.0 的目标不是继续扩展当前的“磁力下载管理系统”，而是将项目收敛为一个通用的资源采集平台：

```text
Go 控制平面 + 浏览器执行服务 + PostgreSQL
```

云盘下载、aria2 下载、STRM 生成和下载后处理不再属于 v2.0 核心链路，后续通过插件接入。

本次设计允许直接替换现有 `magnets` 业务模型。现有数据通过一次正式迁移进入新的通用资源表，不保留 `magnets` 作为投影表。

## 2. v2.0 范围

### 2.1 核心范围

- 动态采集源和采集工作流配置。
- 定时、手动和 API 触发采集。
- 列表页、详情页和分页任务编排。
- 普通 HTTP 页面和浏览器渲染页面采集。
- CSS/XPath/JSONPath 等声明式字段提取。
- 结构化数据转换、校验和去重。
- 原始页面、提取结果和任务过程持久化。
- 通用资源数据保存。
- 磁力资源数据兼容和历史迁移。
- 采集运行历史、任务重试和失败排查。
- Web UI/API 管理工作流和资源。

### 2.2 明确移出核心范围

以下功能不再随 v2.0 控制平面启动：

- aria2 客户端和下载任务管理。
- 云盘离线下载提交和状态轮询。
- 下载完成后的文件移动。
- STRM 文件生成。
- 播放文件信息维护。
- 下载完成/失败状态和下载重试。
- 采集结果自动提交下载。

这些能力保留在独立项目或后续插件中，不参与采集资源状态流转。

## 3. 总体架构

```text
                         ┌────────────────────────┐
                         │       Web UI / API       │
                         └───────────┬────────────┘
                                     │
                         ┌───────────▼────────────┐
                         │       Go 控制平面        │
                         │                          │
                         │ workflow / scheduler   │
                         │ run / task / extractor │
                         │ resource / audit       │
                         └───────┬────────┬─────────┘
                                 │        │
                   ┌────────────▼───┐  ┌─▼──────────────┐
                   │ 浏览器执行服务  │  │   PostgreSQL    │
                   │ drission-rod   │  │ 状态与数据中心   │
                   └────────────────┘  └────────────────┘
```

### 3.1 Go 控制平面

控制平面负责业务编排和数据一致性：

- 工作流定义、版本和发布。
- 采集源管理。
- 调度和任务生命周期。
- 浏览器执行服务调用。
- 页面内容和提取结果保存。
- 规则提取、转换、校验和去重。
- 通用资源入库。
- 运行历史、错误和审计。
- 用户认证、权限和管理界面。

控制平面不直接依赖云盘、aria2 或具体下载器。

### 3.1.1 前端管理界面

前端管理界面属于 Go 控制平面的管理入口，负责工作流、运行过程、任务异常和资源结果的可视化，不再承担下载管理职责。

前端 v2.0 的业务工作区为：

```text
仪表盘
  ├── 采集源
  ├── 工作流
  ├── 运行记录
  ├── 任务队列
  ├── 资源中心
  └── 原始文档
```

前端页面、路由、组件、TypeScript 类型和交互细节以《前端管理界面 v2.0 优化改造方案》为准。主方案只约束领域边界和后端接口，不重复定义页面实现细节。

前端必须遵循以下约束：

- 资源页面展示采集资源，不展示下载生命周期。
- 运行页面展示 Run/Task/Attempt 过程，并支持失败排查和重试。
- 工作流页面支持草稿、校验、发布、版本和回滚。
- 原始文档页面支持安全预览和规则重放。
- 未配置 aria2、cloud-driver 时核心菜单和页面仍然可用。

### 3.2 浏览器执行服务

`drission-rod` 演进为通用浏览器执行服务，不再按站点增加 RPC 方法。

当前的 `FetchJavDB`、`FetchSehuatang` 等接口应逐步统一为通用 Browser Job 接口，站点差异由工作流动作或 recipe 表达。

Browser Job 至少需要支持：

- URL 导航。
- profile/session 选择。
- 等待页面、元素或网络响应。
- 点击、输入和滚动。
- 执行受限 JavaScript。
- 返回 HTML、文本、JSON、截图和 Cookies。
- 超时、取消和结构化错误。

示例请求：

```json
{
  "url": "https://example.com/list",
  "profile_id": "javdb-main",
  "timeout_seconds": 300,
  "actions": [
    {"type": "wait", "selector": ".movie-list"},
    {"type": "click", "selector": ".over18-confirm"}
  ],
  "outputs": ["html", "screenshot"]
}
```

浏览器服务可以保留 JavDB 登录、验证码、弹窗等实现细节，但这些细节不应继续扩展为控制平面中的站点专用接口。

### 3.3 PostgreSQL

PostgreSQL 是 v2.0 的唯一业务状态中心，保存：

- 工作流和版本。
- 运行、任务和执行尝试。
- 原始页面和执行产物。
- 通用资源及其链接。
- 规则校验、重复检测和审计信息。

初期不引入 Redis、Kafka 或其他消息基础设施。任务持久化、领取、重试和事件记录优先使用 PostgreSQL 完成。

## 4. 核心领域模型

### 4.1 Source

采集源是稳定的业务标识，例如：

```text
javdb
javdb-actors
sehuatang
```

源的显示名称、默认入口和工作流关联都进入数据库，不依赖代码中的名称匹配。

### 4.2 Workflow

工作流描述如何从一个或多个入口采集并生成资源，包含：

- 触发配置。
- 起始 URL。
- 浏览器 profile。
- 页面动作。
- 列表发现规则。
- 分页规则。
- 详情页规则。
- 字段提取规则。
- 转换和校验规则。
- 去重规则。
- 输出资源类型。

工作流必须版本化。运行记录引用具体版本，不能只引用当前工作流。

### 4.3 Run、Task、Attempt

```text
workflow_run
└── crawl_task
    ├── task_attempt
    ├── task_attempt
    └── child crawl_task
```

- `workflow_run`：一次完整的手动、定时或 API 采集。
- `crawl_task`：一个逻辑页面任务或工作流步骤。
- `task_attempt`：该任务的一次实际执行。

任务必须支持持久化、重试退避、租约、取消、死信和服务重启恢复。

### 4.4 Document

Document 保存可重放的原始输入和执行结果：

- HTML。
- JSON。
- 纯文本。
- 截图。
- 网络响应摘要。
- 页面元信息。

保存原始文档的目的是让规则调试和版本回放不必重复访问目标站点。

### 4.5 Resource

`resources` 是 v2.0 的通用资源主表，不再使用 `magnets` 作为平台核心表名。

磁力链接是其中一种资源类型：

```text
resource_type = magnet
```

后续可以增加视频、文章、图片等类型，而不修改采集任务模型。

## 5. 数据库设计

### 5.1 sources

```text
sources
- id
- code                 varchar(64), unique
- name                 varchar(128)
- enabled              boolean
- config               jsonb
- created_at
- updated_at
```

`code` 是稳定标识，不能因为显示名称变化而改变。

### 5.2 workflows

```text
workflows
- id
- source_id
- code                 varchar(128)
- name                 varchar(256)
- resource_type        varchar(64)
- enabled              boolean
- published_version_id bigint null
- created_at
- updated_at
```

### 5.3 workflow_versions

```text
workflow_versions
- id
- workflow_id
- version              integer
- status               varchar(32)
- definition           jsonb
- created_by
- created_at
- published_at
```

`definition` 保存工作流 DSL。发布后的版本不可原地修改，只能创建新版本。

### 5.4 workflow_runs

```text
workflow_runs
- id
- workflow_id
- workflow_version_id
- trigger_type         varchar(32)
- status               varchar(32)
- input                jsonb
- summary              jsonb
- started_at
- finished_at
- created_by
- created_at
```

运行状态建议：

```text
pending
running
succeeded
partial_failed
failed
cancelled
interrupted
```

### 5.5 crawl_tasks

```text
crawl_tasks
- id
- run_id
- parent_task_id       bigint null
- step_name            varchar(128)
- task_type            varchar(64)
- input                jsonb
- status               varchar(32)
- attempt_count        integer
- max_attempts         integer
- next_retry_at        timestamp null

- lease_until          timestamp null
- output_document_id   bigint null

```

任务状态建议：

```text
queued
running
retry_wait
succeeded
skipped
failed
dead_letter
cancelled
interrupted
```

### 5.6 task_attempts

```text
task_attempts
- id
- task_id
- attempt_no
- worker_id
- status
- started_at
- finished_at
- duration_ms
- request_snapshot jsonb
- response_snapshot jsonb
- error_message
```

### 5.7 documents

```text
documents
- id
- task_id
- document_type        varchar(32)
- content              text or bytea
- content_hash         varchar(128)
- content_size         bigint
- metadata             jsonb
- created_at
```

大文件可以后续迁移到对象存储，数据库只保存 URI 和摘要；v2.0 初期可以直接存 PostgreSQL，具体由数据量决定。

### 5.8 resources

```text
resources
- id
- resource_type        varchar(64)
- source_id            bigint
- source_url           text
- canonical_key        varchar(512)
- title                text
- status               varchar(32)
- attributes           jsonb
- first_seen_at
- last_seen_at
- created_at
- updated_at
```

建议对以下组合建立唯一约束：

```text
(source_id, resource_type, canonical_key)
```

如果某些源无法生成稳定的业务编号，则使用规范化 URL 或内容哈希作为 `canonical_key`。

资源状态属于采集平台本身，不包含下载状态：

```text
discovered
collected
validated
invalid
duplicate
archived
```

### 5.9 resource_links

```text
resource_links
- id
- resource_id
- link_type            varchar(32)
- link
- name
- priority             integer
- is_optimal           boolean
- metadata             jsonb
- created_at
```

磁力资源的多个链接拆成多行，不再把链接列表和优选链接分别存成字段。

### 5.10 resource_events

```text
resource_events
- id
- resource_id
- event_type
- message
- data                 jsonb
- created_at
```

用于记录新增、更新、重复、校验失败和人工修改等资源事件。

## 6. 现有磁力数据迁移

### 6.1 迁移原则

- 现有 `magnets` 数据全部迁移到 `resources` 和 `resource_links`。
- 不保留 `magnets` 作为新系统的投影表。
- 尽量保留原有主键，降低外部引用和历史排查成本。
- 下载相关信息不进入新的资源核心状态。
- 迁移前必须完成数据库备份和数据校验。

### 6.2 字段映射

| 旧 `magnets` 字段 | 新位置 | 说明 |
| --- | --- | --- |
| `id` | `resources.id` | 建议保留原值 |
| `origin` | `sources.code` | 先建立源映射 |
| `title` | `resources.title` | 直接迁移 |
| `number` | `resources.canonical_key` | 统一转大写并清理空白 |
| `raw_url_host` + `raw_url_path` | `resources.source_url` | 重新拼接为完整 URL |
| `actress0` | `resources.attributes.actress` | 过渡为 JSON 字段 |
| `links` | `resource_links` | 每个链接生成一行 |
| `optimal_link` | `resource_links.is_optimal` | 匹配后标记优选 |
| `status` | `resources.status` | 按采集语义重新映射 |
| `followed_by` 等下载字段 | 归档表或丢弃 | 不进入 v2.0 核心模型 |

当前迁移实现采用以下确定性规则：`origin` 去除首尾空白并转为小写作为
`sources.code`，原始值保存在 `sources.name`；`number` 去除所有 Unicode 空白并转为大写；
无法生成番号时依次回退到规范化来源 URL 和 `legacy-id:<旧 ID>`。同一来源、类型和
规范化番号重复时，首条记录保留原键，后续记录标记为 `duplicate` 并追加
`#duplicate:<旧 ID>` 后缀，以便在唯一约束下保留全部历史数据。

### 6.3 旧状态迁移

旧 `status` 同时混合了采集和下载语义，迁移时不能直接复制数值。

建议按以下规则转换：

```text
有有效标题和链接       -> collected
缺少必要字段            -> invalid
重复资源                -> duplicate
历史状态无法确认        -> collected
```

下载完成、下载失败、STRM 和播放信息不改变新的资源采集状态。

如果需要保留历史下载信息，新增：

```text
legacy_download_states
- resource_id
- followed_by
- old_status
- old_data jsonb
- migrated_at
```

该表只用于历史查询，不被 v2.0 采集流程读取。

### 6.4 迁移执行步骤

1. 停止采集写入和管理端写操作。
2. 备份 PostgreSQL。
3. 创建 v2.0 新表和索引。
4. 创建 `sources` 并建立旧 `origin` 映射。
5. 回填 `resources`。
6. 拆分 `links` 和 `optimal_link` 到 `resource_links`。
7. 按规则迁移采集状态。
8. 可选迁移旧下载状态。
9. 校验数量、唯一键、标题、URL 和链接数量。
10. 切换 Go 仓储层、API 和 UI 到新表。
11. 验证新版本运行稳定后删除旧表。

“一次迁移”指一次正式版本升级，不意味着必须把全部回填放进一个超长事务。数据量较大时应采用分批回填，并在切换前完成校验。

当前 v2.0.1 迁移在 PostgreSQL 单事务中执行建表和回填，并在日志中输出来源、资源、
链接、旧下载状态、旧事件、重复番号、空标题、空番号和无效链接数量。迁移失败会回滚
本版本创建的对象和回填数据，旧 `magnets` 表不会被删除。

## 7. 动态采集工作流

工作流统一抽象为：

```text
Trigger
  -> Acquire
  -> Navigate
  -> Discover
  -> Extract
  -> Transform
  -> Validate
  -> Deduplicate
  -> Persist
  -> Event
```

### 7.1 声明式提取

优先支持：

- CSS selector。
- XPath。
- JSONPath。
- 属性读取。
- 文本清洗。
- 正则捕获。
- 列表和表格提取。
- 下一页和分页参数。

### 7.2 JavaScript 扩展

声明式规则无法处理时允许执行 JS，但脚本必须在沙箱中运行：

- 限制执行时间和内存。
- 禁止访问宿主文件系统。
- 禁止任意网络访问。
- 限制输入和输出大小。
- 记录脚本版本和执行错误。
- 支持测试、发布和回滚。

JS 是扩展步骤，不应替代所有基础提取能力。

### 7.3 AI 提取

AI 作为规则失败后的可选兜底：

```text
声明式提取 -> JS 扩展 -> AI 结构化提取
```

AI 输出必须经过：

- JSON Schema 校验。
- 字段类型转换。
- 必填字段检查。
- 去重校验。
- 置信度判断。

低置信度结果进入人工审核，不直接触发外部插件。

## 8. 插件边界

v2.0 核心不实现下载插件，但应预留事件和插件接口。

资源入库后发布通用事件：

```text
resource.created
resource.updated
resource.validated
```

后续插件可以订阅这些事件：

- cloud-download plugin。
- aria2 plugin。
- Webhook plugin。
- RSS/export plugin。
- 通知 plugin。

插件任务单独保存：

```text
plugin_tasks
- id
- resource_id
- plugin_code
- status
- idempotency_key
- external_task_id
- request jsonb
- response jsonb
- error_message
- retry_count
- created_at
- updated_at
```

插件不能直接修改资源采集状态，也不能直接依赖控制平面的内部数据库对象。

## 9. v2.0 模块调整

### 9.1 保留并重构

- `internal/crawler`：改造成工作流任务执行和持久化任务层。
- `internal/crawler/providers`：短期保留为兼容 provider，逐步迁移为工作流 recipe。
- `internal/drission_rod`：改造成通用浏览器服务客户端。
- `internal/db`、`internal/repo`：围绕新资源模型和任务模型重构。
- `internal/api`：增加 source、workflow、run、task、resource、document API。
- `ui`：按 [前端管理界面 v2.0 优化改造方案](./前端管理界面v2.0优化改造方案.md) 改造成采集源、工作流、运行记录、任务队列、资源中心和原始文档管理界面。

### 9.2 前端接口边界

v2.0 建议使用独立的 `/api/v2` 领域接口：

```text
/api/v2/sources
/api/v2/workflows
/api/v2/runs
/api/v2/tasks
/api/v2/resources
/api/v2/documents
```

旧的 `/api/v1/magnets`、`/api/v1/download`、`/api/v1/cloud-driver` 只在迁移期保留兼容，不作为新前端功能的依赖。前端 API 模块和 TypeScript 类型应按上述领域重新组织。

### 9.3 移除或隔离

- `internal/downloader/aria2_downloader`。
- `internal/downloader/cloud_downloader`。
- 下载调度器和下载状态补偿任务。
- STRM 和播放后处理逻辑。
- 云盘、aria2 相关配置和健康检查。
- 采集成功后自动下载逻辑。

相关代码可以先从主启动流程移除，再在后续插件项目中恢复，不要求 v2.0 首次提交立即物理删除所有历史文件。

## 10. 实施阶段

### 阶段一：核心边界收敛

- 从启动流程移除云盘、aria2 和 STRM 服务。
- 采集成功只负责保存资源。
- 明确资源状态不包含下载语义。
- 定义 Browser Job 协议。
- 前端移除下载管理、Aria2、播放与 STRM 核心菜单。
- 前端仪表盘移除下载统计，改为资源、运行和任务统计。

### 阶段二：新数据库模型

- 创建 sources、workflows、runs、tasks、documents、resources 和 links 表。
- 实现旧 `magnets` 数据迁移脚本。
- 改造 repo、API 和 UI 查询。
- 完成迁移校验和切换。
- 前端将 `/magnets` 迁移为资源中心，并切换到资源 API。
- 前端完成资源详情、资源链接和资源状态展示。

### 阶段三：任务持久化

- 任务入库和数据库领取。
- 租约和并发控制。
- 指数退避和死信。

## 11. 验收标准

v2.0 核心版本至少满足：

- 不依赖 aria2、云盘服务或本地下载目录即可启动。
- JavDB、SeHuaTang 现有磁力数据可以完成迁移。
- 迁移后资源数量、关键字段和链接数量可校验。
- `resources` 可以表达现有磁力数据，不依赖 `magnets` 表。
- 新增采集任务具有 run/task/attempt 追踪信息。
- 任务失败支持延迟重试和最终失败记录。
- 浏览器服务不需要为每个新站点新增 gRPC 方法。
- 工作流规则可版本化，并可针对历史文档重放。
- 采集结果入库不触发下载行为。
- 未来插件可以通过资源事件和独立任务接入。
- 核心前端不配置 aria2、cloud-driver 也可以正常使用。
- 前端生产导航不再展示下载、Aria2、播放和 STRM 核心页面。
- 用户可以从工作流提交入口获得 Run ID，并查看完整运行详情。
- 用户可以查看资源、资源链接、来源文档和资源事件。
- 工作流可以在前端完成草稿、校验、发布和版本回滚。

## 12. 设计原则

1. 采集资源和外部动作分离。
2. 采集状态和下载状态分离。
3. 工作流配置和部署配置分离。
4. 规则版本不可变，运行必须绑定版本。
5. 原始输入可保存、可重放、可审计。
6. 站点差异通过 recipe、脚本或插件表达，不扩展核心协议方法。
7. PostgreSQL 先承担持久化队列和状态中心，规模不足前不引入额外基础设施。
8. AI 只作为结构化提取的受控补充，不能绕过校验和去重。
9. 前端领域命名、路由和类型必须与控制平面的新数据模型保持一致。
10. 前端专项页面设计以《前端管理界面 v2.0 优化改造方案》为实施依据。

- [ ] 统计 token、耗时和失败成本。

## 14. 第一批开发顺序

实际落地时建议按下面顺序推进，不要先做 UI 或 AI：

```text
P0-01 ~ P0-03  核心边界收敛
        ↓
P0-04 ~ P0-07  数据库模型和数据迁移
        ↓
P0-08 ~ P0-10  持久化任务和运行历史
        ↓
P0-11 ~ P0-13  通用浏览器协议
        ↓
P1-14 ~ P1-17  动态工作流和声明式提取
        ↓
P1-18 ~ P1-21  UI、审计和可观测性
        ↓
P2-22 ~ P2-25  JS、插件和 AI
```

每完成一个阶段，都应执行一次完整回归：

- 新建工作流。
- 手动触发采集。
- 产生列表和详情子任务。
- 页面解析成功并保存资源。
- 重复资源被正确识别。
- 任务失败后按退避策略重试。
- 服务重启后任务状态可恢复。
- 不配置下载服务时核心平台仍然正常运行。
