# scrapio v2.1 产品规划

> 状态：产品方向草案
>
> 面向：自用或小团队、单实例部署
>
> 与 v2.0 的关系：v2.0 是从专用磁力采集系统走向平台的技术改造记录；本文重新定义产品目标与验收口径，不以现有模块、表结构或界面形态作为产品边界。

> 命名：产品与主采集平台统一称为 **scrapio**；浏览器执行服务称为 **scrapio-browser**。本文中的“平台”“控制平面”“浏览器服务”描述职责，不代表另一个项目名称。PostgreSQL 是部署依赖。

## 1. 产品定位

scrapio 帮助使用者围绕一个持续的信息需求，建立和维护可信的数据来源。使用者把网页或接口中的信息转成可查询、可追溯、可持续更新的数据，并能知道数据何时失效、为什么失效、如何修复。常见页面与数据类型不需要修改平台代码。

平台的核心承诺是：

> 给定一个可访问的目标、几份代表性样例和期望输出，使用者可以配置采集规则，看到逐步预览，发布后持续获得可信的数据；页面变化时可以用保存的样例定位并修正规则。

“可配置”必须覆盖**获取、发现、提取、转换、校验、去重、保存和调度**的最小闭环，而不只是允许填写一份 JSON。通用性以跨站点、跨资源类型的真实用例验收，不以支持的节点数量衡量。

### 1.1 产品价值与使用周期

产品需要同时回答四个问题：**我要持续收集什么？当前拿到了什么？结果是否可信？出现变化后谁来处理？** 首次配置只是使用周期的起点；长期价值来自数据的持续更新、质量提示、历史追溯和规则可维护性。

典型使用周期是：建立采集项目和目标数据集 → 接入一个或多个来源 → 验证并发布采集器 → 持续运行 → 查看数据变化和质量 → 修复失效来源 → 查询或导出数据。界面优先呈现项目和数据结果，底层运行对象在需要诊断时逐层展开。

### 1.2 目标用户与使用环境

- **规则维护者**：了解目标页面，能指出需要的字段，期望通过界面配置和调试采集器。
- **数据使用者**：查询、筛选、导出已采集数据，关心来源、更新时间和字段质量。
- **实例管理员**：维护 scrapio-browser、凭据、运行容量与故障恢复。小团队中这些角色可以由同一人承担。

默认单实例、少量可信用户协作。不为多租户隔离、计费或大规模分布式调度增加首版复杂度。保留用户身份和操作记录，避免多人修改规则时无法追溯。

### 1.3 主要使用场景

1. 从单个详情页提取文章、商品或视频信息。
2. 从列表页发现详情链接，采集多条记录，并在受控范围内翻页。
3. 从返回 JSON 的接口采集记录。
4. 对需要浏览器渲染、登录态或少量页面交互的站点进行采集。
5. 目标页面变动后，通过历史样例重放、比较字段差异并发布修订版本。

磁力采集是上述场景之一，作为迁移与兼容样例保留，不定义平台的默认数据模型。

## 2. 产品边界

### 2.1 v2.1 核心能力

- 创建、测试、发布和运行采集器。
- 管理页面样例、规则版本和运行历史。
- 保存原始输入、结构化记录及其来源关系。
- 提供字段级结果预览、数据质量提示和失败定位。
- 支持手动、定时及 API 触发；每一种展示在界面的触发方式都必须真实可用。
- 为常见站点提供 HTTP、JSON 和浏览器获取方式。

### 2.2 不纳入 v2.1 核心承诺

- 下载、云盘离线任务、STRM 和媒体后处理；它们属于可选的下游集成。
- 任意形状的可视化流程画布、无限层级的抓取图和分布式爬虫集群。
- 自动破解验证码、绕过网站限制或保证任意网站零配置可采集。
- 运行时默认调用 AI、自动执行下载插件或自动批准低置信度数据。

这些能力可以在后续阶段扩展，但不作为“通用采集”的前提。平台应明确告诉使用者某个目标需要自定义脚本、人工操作，还是当前不支持。

### 2.3 产品组成与命名边界

| 名称 | 职责 | 部署关系 |
| --- | --- | --- |
| `scrapio` | Go 控制平面及管理界面；管理项目、采集器、数据集、调度、运行和持久化 | 主采集平台 |
| `scrapio-browser` | 执行浏览器渲染、页面交互及页面内容获取，并向控制平面返回执行结果 | 独立浏览器服务，由 scrapio 调用 |
| PostgreSQL | 保存平台业务数据、采集记录、任务和运行历史 | 数据库依赖，不作为产品或服务名称 |

普通 HTTP/JSON 获取由 scrapio 的采集流程组织；需要浏览器的步骤交给 scrapio-browser。两个服务使用同一套采集器定义与运行追溯语义，用户无需先理解服务划分才能配置采集任务。

## 3. 用户可理解的产品对象

| 对象 | 用户视角 | 关键关系 |
| --- | --- | --- |
| 采集项目 | 围绕一个信息目标长期维护的工作空间 | 汇总目标数据集、采集器、健康状态、成员和交付方式；单实例默认提供一个项目，按需再建 |
| 采集器 | 一个可运行、可维护的采集方案 | 包含入口、获取方式、页面流程、输出定义、调度和发布版本 |
| 数据集 | 某一类结构化结果的集合 | 定义字段、唯一键、质量规则；可接收一个或多个采集器的结果 |
| 页面样例 | 用来开发和回归规则的真实输入 | 标注页面角色与预期字段，可关联规则版本 |
| 运行 | 一次手动、定时或 API 执行 | 展示版本、范围、成功/失败/跳过数量和时间 |
| 页面任务 | 一次列表、分页或详情获取 | 可追溯输入 URL、页面、提取结果与派生任务 |
| 记录 | 数据集中的一条业务数据 | 保留字段、唯一键、来源、首次/最近发现时间和变更历史 |
| 凭据/会话 | 访问目标所需的授权配置 | 以引用方式绑定采集器，不把秘密写进规则或样例 |

**项目是业务目标入口，采集器是规则维护入口，数据集是结果使用入口。**项目提供轻量组织和健康汇总，不引入租户隔离或复杂权限；新用户可直接使用默认项目创建采集器。站点或采集源可以作为组织与默认设置，但不要求用户先创建“源”再理解“工作流”才能试采。数据集独立于站点：同类记录可以来自不同页面，站点也可以产出多种数据。

## 4. 核心用户旅程

### 4.1 从目标到首次有效数据

1. 确定采集项目的目标数据和用途，选择已有数据集或创建新数据集；默认项目可省略这一步的项目选择。
2. 输入目标 URL 或接口地址，选择单页、列表到详情、分页列表或 JSON 接口模板。
3. 选择获取方式：普通 HTTP、浏览器渲染；必要时引用凭据或浏览器会话。
4. 抓取并保存一份样例。界面展示最终 URL、响应状态、页面内容和截图（如适用）。
5. 对列表页标注记录链接；对分页页标注下一页规则和最大页数；对详情页标注字段。
6. 定义或补全数据集的唯一键、必填字段、字段类型与缺失处理。
7. 运行预览：显示每一步输入、发现的 URL、每条候选记录、字段值、校验结果及预计入库动作。
8. 保存几份覆盖常见变化的样例，运行回归测试，发布不可变版本。
9. 配置手动、定时或 API 触发；首次正式运行后直接查看数据集中的新记录和来源。

预览默认不写正式数据、不触发插件。发布前必须能清楚回答：“会访问哪些页面、最多派生多少任务、会保存什么数据、什么情况下失败或跳过？”

### 4.2 页面变化后的维护

运行异常或数据质量下降 → 打开失败页面/字段 → 对比历史样例与当前页面 → 在草稿中修改规则 → 用样例集回归 → 查看新旧版本的记录差异 → 发布或回滚。

发布后的运行固定引用发布版本。历史运行与历史文档仍可用原版本复现，不因编辑草稿而改变。

### 4.3 日常使用与数据消费

使用者从项目概览进入，先看到数据集最近一次有效更新、最近新增/变化的记录、来源健康与待处理问题。数据使用者可筛选、查看来源并导出记录；维护者可从质量异常直接进入受影响的采集器或页面。新增一个来源时，优先复用已有数据集，使同类数据在同一处查询；不同来源的记录按数据集唯一键合并并保留来源证据。

## 5. 采集器能力模型

### 5.1 首版提供有约束的流程模板

| 模板 | 输入 | 可配置步骤 | 边界 |
| --- | --- | --- | --- |
| 单页详情 | 一个或多个 URL | 获取 → 提取 → 校验 → 保存 | 不自动发现其他页面 |
| 列表到详情 | 列表 URL | 获取列表 → 发现详情 URL → 获取详情 → 提取 → 保存 | 详情去重，限制每页发现数量 |
| 分页列表 | 起始 URL | 列表发现 + 下一页发现 + 详情处理 | 必填最大页数、最大任务数和停止条件 |
| JSON 接口 | URL、方法和受限参数 | 获取 JSON → 列表路径 → 字段提取 → 保存 | 不要求浏览器参与 |

模板生成可编辑的规则，但发布时仍按同一执行契约校验。后续可以增加模板，不让模板之间形成不同的任务、记录和错误语义。

### 5.2 获取页面

- HTTP 与浏览器采用统一的获取结果：请求信息、最终 URL、状态、内容类型、正文、时间、错误及可选截图。
- 浏览器动作首版优先支持导航、等待元素、点击、输入和滚动；动作的执行位置、顺序、超时和错误可在预览中看到。
- 浏览器 profile、请求头、Cookies、页面复用等只有在执行服务真正支持并经过联调后才成为可配置选项。
- 每个采集器配置目标域名、超时、请求间隔、并发、最大页面数和最大运行时长。跨域发现默认需要明确允许。

### 5.3 发现和提取

- 列表发现输出标准化 URL，负责相对路径解析、去重和派生数量预估。
- 分页有停止条件：达到最大页数、无下一页、重复下一页或连续空页。
- 字段规则支持 CSS、XPath、JSONPath、属性读取、正则捕获、清洗与基础类型转换。
- 每个字段展示原始值、转换值、来源位置、校验错误；提取失败与页面获取失败分开呈现。
- 允许声明字段是单值还是多值、必填还是可空，避免用空字符串掩盖解析失败。

### 5.4 记录保存与去重

- 数据集定义 `record_type`、显示字段、唯一键字段及字段 Schema，不预设 `number`、`links` 等磁力字段。
- 每条候选记录的保存结果只有：**新增、更新、内容未变、校验不通过、冲突待处理**。一次运行可以同时出现多种结果。
- 唯一键在保存前生成并预览；缺少唯一键不能静默算成功。
- 保留原始字段值、规范化字段值、来源页面、采集器版本及时间。字段更新策略由数据集配置，默认不以空值覆盖已有非空值。
- 磁力资源通过数据集模板和字段映射兼容，不能要求其他资源提供磁力字段。

### 5.5 触发与调度

- 手动运行支持覆盖入口 URL，必须标明本次运行范围和版本。
- 定时运行支持启停、时区、下次运行时间、并发策略（跳过或排队）和历史结果。
- API 触发返回可查询的运行 ID；凭据和允许覆盖的参数由采集器配置控制。
- 运行内设置页面数、任务数、深度和耗时预算。达到预算时明确记录“受限结束”，不冒充完整成功。

## 6. 管理界面与反馈

管理界面的产品结构、日常使用路径、创建向导、配置工作台、数据消费与运行排错见 [scrapio v2.1 管理界面产品设计](前端管理界面v2.1产品设计.md)。

### 6.1 一级工作区

```text
项目        目标、数据概览、来源健康、成员与交付入口
数据        数据集、记录查询、变化、质量与导出
采集器      来源规则、样例、测试、发布、调度
运行        运行列表、页面任务、失败定位、重试
设置        scrapio-browser、凭据、容量与操作记录
```

首页根据项目显示“数据是否持续更新、来源是否健康、谁需要处理什么”，再展示总量统计。用户创建首个采集器时进入向导；熟悉规则的用户可以切换到高级 JSON 编辑。两种编辑方式读写同一份经过版本校验的定义。

### 6.2 采集器编辑页

建议使用“步骤导航 + 当前配置 + 实时预览”的布局。步骤顺序为：目标与模板、获取方式、发现与分页、输出字段、数据集与去重、测试与发布、调度。每一步显示已配置、待补充、测试失败或通过。

测试界面需展示页面级和字段级结果，支持保存为样例、对比版本。发布按钮应列出阻断项与提醒项；未实现的节点或触发器不能通过发布校验。

### 6.3 运行详情

运行顶部展示版本、触发来源、预算、总耗时及“新增/更新/未变/无效/失败”的数量。下方按列表、分页、详情组织页面任务。选中任务可查看请求、原始文档、字段提取、派生链接、最终记录和错误。支持从失败任务直接创建规则草稿或保存样例。

运行状态区分：成功、部分成功、失败、取消、受限结束；页面跳过和重复记录计入结果统计，不自动视为错误。

## 7. 质量、信任与可观察性

- **样例回归**：一个采集器至少能保存正常详情、字段缺失、空列表等样例；发布前执行相关样例测试。
- **字段质量**：记录必填字段缺失率、唯一键生成率、异常值比例和近几次运行趋势。阈值可配置，超阈值提醒维护者。
- **可追溯**：从记录可回到来源文档、运行、页面任务与规则版本；从字段错误可回到实际提取规则。
- **明确失败**：配置未实现、浏览器不支持、页面超时、提取失败、校验失败、去重冲突分别报告，避免用“运行成功但入库 0 条”覆盖问题。
- **可控存储**：原始文档和截图有保留期、大小上限和清理策略。被样例引用的文档不随普通清理删除。

## 8. 扩展方向及进入条件

### 8.1 JavaScript

在声明式规则不足以表达目标时，允许两类脚本：浏览器内页面动作、控制平面内纯数据转换。分别明确输入、输出、权限、超时、大小限制和版本。脚本应有样例测试及发布记录，不能通过访问宿主文件系统或任意网络来绕过平台边界。

### 8.2 AI

优先用于**辅助生成字段规则、解释失败和建议修复**，由使用者检查后保存为普通规则。运行时结构化提取仅作为显式开启的策略，需要输入裁剪、成本上限、Schema 校验、置信度和人工复核。AI 结果与普通规则结果一样可追溯到输入文档和模型版本。

### 8.3 插件和外部动作

采集结果确认后才向显式订阅的插件投递事件。插件负责通知、导出、下载等下游动作，有独立的运行历史、重试和幂等键。插件失败不改变采集记录的结果；采集器发布时必须展示可能触发的外部动作。v2.1 可以只提供事件契约与少量受控集成，不以插件数量作为产品成熟度指标。

## 9. 分阶段交付与验收

### A. 从目标到可信的第一条数据

交付默认项目、单页详情和 JSON 接口模板、通用数据集、样例预览、版本发布及运行追溯。验收：分别创建一个非磁力数据集和一个磁力数据集，不改平台代码完成提取与入库；首次正式运行后能从项目页找到记录及来源；不支持的配置不能发布。

### B. 持续采集与日常使用

交付列表到详情、受控分页、调度、预算、页面任务树、项目健康概览、数据变化与部分成功状态。验收：再次打开项目时能判断数据是否更新、来源是否健康；运行能说明访问了多少页、发现多少链接、哪些详情失败及为什么结束；服务重启后不会丢失待处理任务。

### C. 质量恢复与协作维护

交付样例集、字段级调试、版本差异、历史文档回放、质量提醒和负责人/变更摘要。验收：模拟目标页面结构变化，从项目待办进入问题，不重新访问目标站点也能定位坏掉的字段、验证修订并回滚；修复后项目健康状态恢复。

### D. 可选扩展

在前三阶段稳定后加入脚本版本、显式插件订阅和 AI 辅助。每项都有独立验收，不能用扩展功能补偿基础采集链路的缺口。

每阶段只把“从界面能完成、在真实运行中有结果、失败可解释”的能力标为已交付。已有代码是否存在某个结构或接口，不单独构成验收。

## 10. 产品指标

以下是首轮试用的目标值，用于发现体验问题，实际阈值可随样例站点难度调整：

| 指标 | 初始目标 | 测量方式 |
| --- | --- | --- |
| 新站点首次正确入库时间 | 普通单页不超过 30 分钟；列表到详情不超过 2 小时 | 从创建采集器到首个有效记录入库 |
| 数据可用时间 | 首次正式运行后不超过 2 分钟找到、筛选并查看记录来源 | 从运行完成到数据使用者完成一次查询 |
| 来源健康感知 | 失效来源在下次运行后于项目概览明确出现 | 用故意失效的规则和样例演练 |
| 常见场景无代码覆盖率 | 选定的单页、列表详情、JSON 样例全部无需改代码 | 使用至少 3 个不同站点、2 类数据集验收 |
| 发布前可预测性 | 样例测试能展示预计访问范围和每条记录的保存决策 | 发布评审逐项检查 |
| 问题定位时间 | 一次字段解析回归在 10 分钟内定位到页面及规则 | 使用历史样例演练 |
| 静默成功 | 0 次 | 配置未执行、唯一键缺失或预算截断都必须有明确结果 |

## 11. 与 v2.0 的衔接

现有控制平面、浏览器服务、PostgreSQL、资源迁移和运行记录可作为实现基础；命名统一为 scrapio 与 scrapio-browser 不意味着此时改动仓库目录、代码包路径或部署配置。v2.1 的设计与验收以本文件为准。下一步应先用本文件的对象和用户旅程梳理现有功能，再形成单独的技术差距清单与实施计划；不直接把 v2.0 未勾选的 TODO 全部搬入 v2.1。

特别需要核对：采集器与数据集能否真正脱离磁力字段；编辑器与发布校验是否只提供可执行能力；HTTP/浏览器获取是否符合预览契约；样例测试是否覆盖完整流程；资源、页面任务和版本之间是否能互相追溯。

## 12. 待验证的产品决策

1. 首轮试用的三个样例站点及两类数据集由实际使用者选定，避免只用同一种页面验证通用性。
2. 默认项目能否承载首次使用；多个信息目标出现后，项目分组是否足够清晰，采集源继续作为可选的共享配置。
3. 记录更新策略的默认值：整条替换、逐字段合并，或由数据集按字段配置。本文暂定逐字段合并且空值不覆盖非空值。
4. 普通 HTTP 与浏览器采集的默认选择、切换提示和资源预算，需要结合目标站点测试确定。
5. 页面样例、原始文档和截图的默认保留期，需要根据单实例的磁盘容量确定。
